# ADR-004: Idempotency-Key на входящих POST-запросах

## Контекст
В [ADR-003](adr-003-additional-info-request-flow.md) (раздел "Открытые вопросы") идемпотентность клиентских запросов была осознанно
отложена вместе с авторизацией клиентских эндпоинтов и трассировкой — прорабатывается отдельным
проходом по всему API. [ADR-002](adr-002-idempotent-account-creation.md) покрывает только внутреннюю идемпотентность создания счёта
в Core Banking (по `application_id`), а не входящие запросы от клиента и менеджера.

Без ключа идемпотентности повтор запроса при обрыве сети/таймауте (клиент не получил ответ и не
знает, применилось ли действие) может привести к двойной обработке:
- `POST /application` — риск создать вторую заявку на те же данные.
- `POST /application/{id}/additional-info`, `POST /application/{id}/documents` — оба
  асинхронные (`202`), окно между приёмом запроса и фактическим применением состояния (`ADDITIONAL_INFO_REQUIRED`)
  открыто дольше, повтор в этом окне может задвоить обработку.
- `POST /application/{id}/approve`, `/reject`, `/request-additional-info` — синхронные, уже
  защищены проверкой текущего статуса (`409`, если не `MANUAL_REVIEW`), но при гонке (менеджер
  кликает дважды быстро, оба запроса читают статус до того, как первый закоммитится) проверка
  статуса это не ловит.

## Решение
- Все 6 `POST`-эндпоинтов (`postApplication`, `submitAdditionalInfo`, `submitAdditionalDocuments`,
  `approveApplication`, `requestAdditionalInfo`, `rejectApplication`) требуют обязательный заголовок
  `Idempotency-key` (UUID, генерируется клиентом) — компонент `#/components/parameters/IdempotencyKey`
  в `api/openapi.yaml`.
- `GET /application/{id}/status` ключ не требует — операция read-only, естественно идемпотентна.
- Поведение сервера при повторном запросе с уже виденным ключом:
  - тело запроса совпадает с исходным — возвращается ранее сохранённый ответ, повторной обработки
    не происходит;
  - тело отличается — `409` (объединён с уже существующим `409` эндпоинта — конфликт с
    текущим состоянием; конкретная причина различается через `errorCode` в `ErrorResponse`).
- Единое правило для всех `POST`, а не точечное только для "рискованных" эндпоинтов — проще для
  клиента и не требует разбирать по каждому эндпоинту отдельно, нужен ли ключ.
- Серверное хранение — таблица `idempotency_keys` (`idempotency_key`, `request_hash`,
  `response_status`, `response_body`, `created_at`, `expires_at`) в `database/schema.sql`. Без
  FK на `application` — используется и в `POST /application`, где заявки ещё не существует.

## Почему
Ключ идемпотентности закрывает случай "клиент не знает, применился ли предыдущий запрос" —
единственный надёжный способ отличить "это тот же самый запрос, повторённый из-за сети" от
"это новый, повторяющий действие по смыслу, запрос" на стороне сервера, а не только эвристикой
по бизнес-состоянию (как сейчас `409` на менеджерских эндпоинтах).

## Открытые вопросы
- Конкретное значение TTL хранения ключа (`idempotency_keys.expires_at`) не зафиксировано —
  вопрос уровня нефункциональных требований, не контракта.
- Авторизация клиентских эндпоинтов решена отдельно в [ADR-005](adr-005-access-token-client-endpoints.md) (`accessToken`) — ключ
  идемпотентности её не заменяет: он защищает от двойной обработки, а не от доступа к чужой
  заявке.
