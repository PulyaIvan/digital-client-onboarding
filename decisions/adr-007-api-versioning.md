# ADR-007: Версионирование API (URI-путь /v1)

## Контекст
До этого момента `api/openapi.yaml` не был версионирован вообще — пути вида `/application/{id}`
без какого-либо признака версии. Это осознанно не мешало, пока контракт активно менялся
(ADR-004/005/006, эндпоинт списка заявок, поле `history` — см. [ADR-006](adr-006-access-recovery-otp.md)
и обсуждение перед ним). Как только контракт стабилизировался и стал считаться закрытым, встал
вопрос: любое будущее breaking-изменение сейчас молча ломает всех клиентов, потому что нет способа
выпустить новую версию, не задев старую.

## Решение
- Версия — в пути: `/v1/application`, `/v1/application/{applicationId}`, ... — префиксом на
  все 11 путей спеки.
- Текущая major-версия — `v1`, соответствует `info.version: 1.0.0`. Пока действует только одна
  версия одновременно — `/v2` не заводится, пока нет реального breaking change, требующего
  сосуществования двух поколений в одном файле.
- Внутри `api/openapi.yaml` все буквальные упоминания путей в описаниях
  (`ApplicationCreateResponse`, `ApplicationListResponse`, `passportScanUrl`/`photoApplicantUrl`)
  обновлены на `/v1/...` вместе с самими путями — источник истины один.
- В ADR/`requirements/*.md` эндпоинты по-прежнему упоминаются в сокращённой форме без `/v1`
  (например "`POST /application`" в тексте ADR-005) — это осознанное сокращение, не рассинхрон:
  `api/openapi.yaml` остаётся единственным источником буквального пути. Более ранние ADR
  (001–006) не переписывались задним числом.

## Почему
- URI-путь — самый явный и самообнаруживаемый вариант: версия видна прямо в URL, не нужно
  заглядывать в заголовки. Для B2C-банковского API, где клиентские приложения собираются один
  раз и редко перечитывают спеку, это снижает риск случайно остаться на не той версии.
  Разработчик, открывший `curl`/браузер, сразу видит версию — не нужен доступ к заголовкам
  запроса, как при header/media-type версионировании.
- Версия в `servers.url` (например `https://api.example.com/v1`, без `/v1` в самих путях)
  рассматривалась и отклонена: делает версию невидимой при чтении конкретного пути в спеке
  (`GET /application/{id}` — непонятно, какая версия), и плохо ложится на будущий сценарий, если
  `/v1` и `/v2` понадобится держать бок о бок в одном файле на переходный период — с версией в
  path это тривиально (`/v1/...` и `/v2/...` как разные path items), с версией в server URL
  пришлось бы заводить два сервера и дублировать все пути под каждый.

## Альтернативы
- **Header/media-type версионирование** (`Accept: application/vnd.onboarding.v1+json` или
  кастомный `Api-Version` заголовок) — отклонено. Формально более "RESTful"-чисто (путь
  остаётся стабильным идентификатором ресурса), но требует от каждого клиента аккуратно
  проставлять заголовок и хуже поддаётся ручной отладке. Оправдано, когда много внешних
  консьюмеров с разным темпом миграции на новую версию — для этого API (одно мобильное/веб
  приложение банка, без внешних партнёров) такой сложности не требуется.
- **Версия в `servers.url`** — отклонено, см. "Почему".
- **Не версионировать** (статус-кво) — отклонено: любое будущее breaking change молча ломает
  всех клиентов без возможности постепенной миграции.

## Открытые вопросы
- Политика устаревания (deprecation policy) для будущего `/v2` — сколько времени `/v1` держится
  параллельно, как клиентов уведомляют (заголовки `Deprecation`/`Sunset`?) — не определено;
  отдельный вопрос на момент, когда реально появится `/v2`.
- `diagrams/sequence/*.puml` называют эндпоинты без версии (`POST /application` и т.п.) —
  сознательное сокращение, не рассинхрон (см. «Решение» выше); диаграммы не перерисовывались
  под `/v1`-префикс, так как он не влияет на последовательность взаимодействия.
