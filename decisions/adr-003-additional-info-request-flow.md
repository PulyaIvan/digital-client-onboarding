# ADR-003: Донесение дополнительных данных по заявке (без черновика/корзины)

## Контекст
Заявка создаётся одним запросом (`POST /application`, все поля и документы обязательны) —
это решение уже принято ранее и данным ADR не пересматривается.

В процессе обработки (автоматическая валидация, KYC, ручная проверка менеджером) может
выясниться, что часть данных нужно донести повторно: нечитаемый скан, расхождение данных,
недостающий документ. Рассматривался вариант завести отдельное состояние "черновик"/"корзина",
куда сохранять неполные данные до их донесения — но это ломает исходную концепцию "заявка
создаётся полной за один запрос" и требует отдельного места хранения незавершённых заявок.

## Решение
- Черновик/корзина не вводится. Заявка, однажды созданная, всегда полна; недостающие данные
  запрашиваются повторно у уже существующей заявки (по `applicationId`), а не создают новую сущность.
- Статусная модель расширена: `PENDING`, `MANUAL_REVIEW`, `ADDITIONAL_INFO_REQUIRED`,
  `APPROVED`, `REJECTED`, `EXPIRED`.
- Переходы:
  - `PENDING` → `MANUAL_REVIEW` / `ADDITIONAL_INFO_REQUIRED` / `APPROVED` / `REJECTED`
    (по результату автопроверки/KYC)
  - `MANUAL_REVIEW` → `APPROVED` / `REJECTED` / `ADDITIONAL_INFO_REQUIRED`
    (решение менеджера, включая запрос доп. информации)
  - `ADDITIONAL_INFO_REQUIRED` → `PENDING` (клиент донёс всё запрошенное в срок — заявка
    возвращается в общую очередь на полную повторную обработку)
  - `ADDITIONAL_INFO_REQUIRED` → `EXPIRED` (истёк `additionalInfoDeadline`, донос не пришёл)
- Переход в `EXPIRED` выполняет фоновый батч-джоб внутри `Onboarding Service` (не отдельный
  сервис, не delayed-сообщение в Kafka): периодически сканирует `application` на
  `status = ADDITIONAL_INFO_REQUIRED AND additional_info_deadline < now()`, переводит каждую
  найденную заявку в `EXPIRED`, пишет `application_history` (`changed_by = null` — системный
  переход, как и остальные автоматические) и публикует клиенту `notification` тем же механизмом,
  что и при входе в `ADDITIONAL_INFO_REQUIRED` (см. ADR-001). Это не отдельная OpenAPI-операция —
  внутренний механизм `Onboarding Service`, клиент узнаёт о переходе через `notification` и/или
  очередной `GET /status`, как и о любом другом статусе.
- TTL на донос данных единый (конкретное значение — 24ч/72ч/др. — не зафиксировано, только сам
  факт одного таймаута), не зависит от того, кто инициировал запрос (система из `PENDING` или
  менеджер из `MANUAL_REVIEW`). Хранится в поле `additionalInfoDeadline` в `ApplicationStatusResponse`.
- `EXPIRED` — терминальный статус без обязательного `reasonCode` (в отличие от `REJECTED`),
  самого факта статуса достаточно.
- Запрос менеджера на донос данных — отдельное действие `POST /application/{id}/request-additional-info`
  (не часть approve/reject), со своим `reasonCode` и списками `requestedFields`/`requestedDocuments` —
  именно они определяют, что клиенту разрешено прислать в ответ.
- Донос от клиента — два отдельных эндпоинта, а не один общий:
  - `POST /application/{id}/additional-info` — текстовые поля (`application/json`)
  - `POST /application/{id}/documents` — документы (`multipart/form-data`)

  Оба — `POST`-действия, а не `PATCH`: это не произвольное редактирование ресурса, а обработка
  конкретного бизнес-события "клиент ответил на запрос доп. информации", допустимая только в
  статусе `ADDITIONAL_INFO_REQUIRED` и запускающая пересчёт/возможный переход статуса.
- Заявка хранит чек-лист того, что было запрошено (`requested_fields`, `requested_documents` —
  см. `database/schema.sql`), и два флага закрытия — `text_info_received`, `documents_received`.
  При входе в `ADDITIONAL_INFO_REQUIRED` оба флага сбрасываются в `false` (пустой чек-лист по
  соответствующей части считается закрытым сразу).
  - `POST /application/{id}/additional-info` принимается только целиком: клиент обязан прислать
    в одном запросе все поля из `requested_fields`, иначе — `400` с перечнем недостающих; при
    успехе `text_info_received = true`.
  - `POST /application/{id}/documents` — симметрично для `requested_documents` и
    `documents_received`.
  - Переход `ADDITIONAL_INFO_REQUIRED → PENDING` происходит, когда обе части закрыты
    (`text_info_received AND documents_received`, с учётом того, что пустой чек-лист уже закрыт).

## Почему
- Отдельная сущность "черновик" добавляла бы второе место хранения неполных заявок и второй
  жизненный цикл — при том что после доноса заявка проходит ту же полную обработку, что и
  обычная. Проще смотреть на это как на состояние уже существующей заявки.
- `PATCH` подразумевает разрешение менять любое поле в любой момент; здесь действие валидно
  только в одном статусе и только для явно запрошенных полей — `POST`-действие точнее выражает
  это ограничение и соответствует уже принятому в API стилю (`approve`/`reject` тоже POST-действия).
- Текст и документы разделены на два эндпоинта, потому что это разные форматы контента
  (`application/json` vs `multipart/form-data`) и разная логика хранения (текст — в БД,
  документы — в vault, см. Sensitive Data / Applicant Document в глоссарии), что уже заложено
  в исходной модели `ApplicationCreateRequest`.
- Приём "только целиком" (а не накопление частичных ответов по каждому полю отдельно) выбран,
  чтобы не заводить дополнительное состояние "что из чек-листа уже пришло по кусочкам" — это
  тот же принцип, что и в исходном решении "заявка создаётся полной за один запрос", просто
  применённый к повторному доносу данных: одного флага на весь эндпоинт достаточно.

## Альтернативы
- Черновик/корзина заявки — отклонено: ломает модель "заявка создаётся полной за один запрос",
  требует отдельного хранилища для неполных заявок.
- `PATCH /application/{id}` вместо отдельных POST-эндпоинтов — отклонено: смешивает семантику
  "изменить поле" с семантикой "ответить на запрос доп. информации", не ограничивает набор
  полей текущим запросом.
- Один общий multipart-эндпоинт для текста и документов сразу (по аналогии с `POST /application`) —
  отклонено: разные форматы контента для по сути двух независимых действий; отдельные
  эндпоинты проще валидировать и документировать по отдельности.
- **Delayed-сообщение в Kafka** для перехода в `EXPIRED` (публикуется при входе в
  `ADDITIONAL_INFO_REQUIRED` с задержкой = TTL, по доставке проверяется актуальность и заявка
  экспайрится) — отклонено: точнее по времени, чем батч-джоб, но требует delayed-очереди/плагина
  для Kafka, которого сейчас нет в архитектуре — не оправдано ради одного перехода.
- **Ленивая проверка дедлайна при чтении** (статус пересчитывается на лету при любом обращении к
  заявке, без фонового процесса) — отклонено: клиент не узнаёт об истечении проактивно (только
  если сам запросит `GET /status`), а списки/отчёты у менеджера могут показывать устаревший
  статус до следующего обращения к конкретной заявке.

## Открытые вопросы
- Конкретное значение TTL (`additionalInfoDeadline`) и интервал опроса батч-джоба не
  зафиксированы — вопрос уровня нефункциональных требований, не архитектуры.
- Защита клиентских эндпоинтов (идемпотентность входящих POST, доступ по `applicationId`) —
  решена в [[adr-004]] (Idempotency-key) и [[adr-005]] (Access-Token, `applicationId` осознанно
  остаётся `int64`, см. её "Альтернативы"). Серверное хранение ключей/токена — тоже сделано,
  `idempotency_keys`/`application_access_token` в `database/schema.sql`.
- Аутентификация менеджерских эндпоинтов (`approve`/`reject`/`request-additional-info`) —
  сделана, `BearerAuth`/JWT задан в `api/openapi.yaml`. Трассировка — заголовок
  `X-Correlation-Id` тоже уже в контракте; диаграммы это пока не отражают, см.
  `requirements/sync-debt.md`.
