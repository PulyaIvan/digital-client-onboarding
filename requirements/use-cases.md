# Акторы, User Stories, Use Case

## Акторы

**Внешние:**
- Client — новый клиент банка
- KYC — процесс проверки личности клиента и оценки риска

**Внутренние:**
- Core Banking — центральная система учёта счетов, балансов и транзакций банка
- Notification Service — система уведомлений
- Kafka (Event Bus) — брокер сообщений для асинхронного взаимодействия между Onboarding Service, Core Banking и Notification Service
- Manager — сотрудник банка, вручную рассматривает заявки в статусе MANUAL_REVIEW через административный интерфейс

## User Stories

### [US-002] Обработка очереди заявок на ручную проверку
Как **Manager**, я хочу видеть список заявок, ожидающих моего решения, и историю уже принятых по заявке решений, чтобы обрабатывать MANUAL_REVIEW системно, а не по угаданным applicationId.

Приоритет: Should | Статус: Draft

Собственного отдельного Use Case не заводится — это предшествующий шаг к сценарию **7c** в Use Case "Открытие счёта" ниже: менеджер сначала получает список заявок в статусе MANUAL_REVIEW (`GET /application?status=MANUAL_REVIEW`), затем открывает конкретную заявку (`GET /application/{applicationId}`, включая `history` — прошлые решения по этой же заявке, если она уже возвращалась из ADDITIONAL_INFO_REQUIRED), и дальше действует по 7c/7d.

### [US-001] Открытие дебетового счёта для нового клиента банка
Как **Client**, я хочу открыть дебетовый счёт онлайн, чтобы не тратить время на визит в отделение банка.

Приоритет: Must | Статус: Draft

## Use Case: Открытие счёта

### Happy Path
1. [Client] нажал на кнопку "Открыть счёт"
2. [Система] предоставляет форму для заполнения персональных данных и загрузки документов (паспорт, фото)
3. [Client] заполняет все необходимые поля, загружает документы и нажимает "Оформить заявку"
4. [Система] валидирует введённые данные и наличие обязательных документов
5. [Система] сохраняет персональные данные и документы, отправляет данные в KYC
6. [KYC] проверяет личность клиента и оценивает риски
7. [KYC] отправляет в систему статус "Approved"
8. [Система] принимает статус "Approved"
9. [Система] создаёт банковский счёт в Core Banking
10. [Система] отправляет уведомление клиенту со статусом "Approved"

### Альтернативные сценарии
- **4a.** Не все обязательные поля заполнены или не загружены обязательные документы → система не пропускает заявку, просит заполнить/загрузить недостающее (подсвечены красным)
- **5a.** KYC-сервис недоступен/не отвечает → клиент видит статус "заявка обрабатывается", результат придёт позже, заявка не теряется
- **7a.** KYC оценил клиента как высокорискованного, статус "Rejected" → заявка отклоняется, клиент уведомляется
- **7b.** KYC вернул статус "Manual Review" → заявка переходит в MANUAL_REVIEW, но клиент продолжает видеть "Заявка обрабатывается"
- **7c.** Заявка в MANUAL_REVIEW → менеджер вручную рассматривает через административный интерфейс (включая загруженные документы), выставляет решение (approved/rejected)
- **7d.** Автопроверка (из PENDING) или менеджер (из MANUAL_REVIEW) обнаруживает устранимую проблему (нечитаемый скан, расхождение данных) → заявка переходит в ADDITIONAL_INFO_REQUIRED с указанием, какие именно поля/документы нужно донести, и сроком (`additionalInfoDeadline`); клиент уведомляется, донoсит недостающее двумя отдельными запросами (текстовые поля / документы) → заявка возвращается в PENDING на полную повторную обработку. Подробности модели статусов и обоснование — см. [ADR-003](../decisions/adr-003-additional-info-request-flow.md)
- **7e.** Заявка в ADDITIONAL_INFO_REQUIRED, клиент не донёс запрошенное до истечения `additionalInfoDeadline` → заявка автоматически переходит в EXPIRED
- **9a.** Ошибка при создании счёта в Core Banking после успешного KYC → клиент не получает преждевременного уведомления об успехе; система гарантирует, что счёт будет создан ровно один раз

## Use Case: Восстановление доступа к заявке (Access Recovery)

Как **Client**, потерявший токен доступа к своей заявке (закрыл вкладку, сменил устройство), я хочу восстановить доступ, чтобы проверить статус или донести данные/документы, не создавая заявку заново.

Приоритет: Should | Статус: Draft

### Happy Path
1. [Client] на форме проверки статуса выбирает "Не могу войти по токену"
2. [Система] запрашивает email, указанный при подаче заявки
3. [Client] вводит email
4. [Система] отправляет на email одноразовый код (если email совпадает с данными заявки; ответ клиенту одинаков в любом случае — см. [ADR-006](../decisions/adr-006-access-recovery-otp.md))
5. [Client] вводит полученный код
6. [Система] подтверждает код и выдаёт новый токен доступа; прежний токен становится недействителен
7. [Client] использует новый токен для проверки статуса/донесения данных

### Альтернативные сценарии
- **4a.** Email не совпадает с данными ни одной заявки → система всё равно отвечает так же, как в 4 (код никуда не уходит) — исключает перебор applicationId/email
- **6a.** Код неверен, истёк или превышено число попыток → единая ошибка "код неверен или истёк", клиент может запросить новый код (шаг 2)
